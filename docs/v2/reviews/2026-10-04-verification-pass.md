## New problems

### A. Gate logic (DESIGN §5.2)

**N-1 — Rule 2(a) re-opens the D-2 hole.** See D-2 row. Fix given there.

**N-2 — Rule 2(c) condition is a tautology; rule 1 hard-codes `public`.** "`B` is the build on `public` at decision time" is the definition of B. Rule 1 says "`public == B_inst`" although the server may track another branch.
Fix: (c) as in the D-2 row; rule 1: "Allowed when the tracked branch's build equals `B_inst` and rule 0 does not apply."

**N-3 — Rule 2(b) can never open for an update whose Oxide release is published before it goes public outside the forced-wipe window.** The forced-wipe window is first-Thursday only. On a mid-month mandatory update (next: 2026-10-22) Oxide very likely publishes before `public`, as it does on wipe day (R-tech §3.5; unverified for mid-month). Then no release has `published_at ≥ T_public(B)`, FMU waits `maxWait` (45 min) and the default `keep-waiting` leaves the server on an unjoinable build until Oxide happens to publish again.
