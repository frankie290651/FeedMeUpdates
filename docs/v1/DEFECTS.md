# FeedMeUpdates v1 — consolidated defect register

This is the single, de-duplicated list of defects and risks found in FeedMeUpdates v1.6.5 (Oxide plugin `FeedMeUpdates.cs`, companion app `Application/Program.cs`, sample scripts in `Scripts/`). It merges the "Defects and risks" sections of the eight behaviour specifications in `docs/v1/spec/` (A1–A4 for the app, P1–P4 for the plugin).

How to read it:

- All findings come from **reading the code**, not from running it. Nothing here was reproduced on a live Rust server. The only thing executed was `bash -n` on the sample start script (D-099).
- "Verified?" = *verified by reading* when the behaviour follows from the v1 source alone; *unverified* when it also depends on third-party behaviour (Oxide, Mono, systemd, tmux, SteamCMD, GitHub, Rust itself) that is not in this repository. The part that is unverified is named.
- Locations: `P:` = `FeedMeUpdates.cs`, `A:` = `Application/Program.cs`, `S:` = `Scripts/`, followed by line numbers.
- Severity: **High** = server left down, data loss, unintended wipe, code execution, or automation silently lost in a plausible scenario. **Medium** = wrong behaviour that needs manual repair or has a workaround. **Low** = cosmetic, unlikely, dead code.
- Where the spec files disagreed, the source was checked; the outcome is in the row and collected in "Reconciliation notes" at the end.
- Totals: 29 High, 71 Medium, 32 Low (132 rows).

## Defect classes and the v2 invariant each one motivates

**server-left-down** — D-001, D-002, D-003, D-004, D-015, D-016, D-025, D-033, D-117, D-131 (10)
Root cause: "bring the server back" is one of many optional steps, repeated by hand at each exit and missing from several (restore, force-wipe exception, crashes, aborted launches). v2 invariant: once the server has been told to stop, every exit path of either program must restart it or raise an alert, verify that it actually came up, and the plugin must not issue `quit` until the updater has confirmed it is running.

**data-loss** — D-012, D-014, D-021, D-022, D-023, D-027, D-056, D-062, D-066, D-068, D-086, D-118 (12)
Root cause: destructive actions use broad matching, destructive defaults and delete-before-replace, with no backup in the wipe flow and the only backup deleted on failure. v2 invariant: every deletion targets an explicit, validated list of file names inside a known directory; replacement is rename-over; a backup is never deleted until the state it protects is verified; destructive options are opt-in and time-based triggers require a future, confirmable schedule.

**hang/no-timeout** — D-006, D-008, D-009, D-010, D-011, D-077, D-128 (7)
Root cause: child processes and waits are written with blocking reads before the timeout, unbounded polling loops and one unterminated string loop. v2 invariant: every wait, child process and network call has a wall-clock deadline enforced by one shared runner (async reads of both pipes, tree kill), and reaching a deadline is a reported failure that still restarts the server.

**security** — D-017, D-018, D-043, D-075, D-114, D-132 (6)
Root cause: values cross trust boundaries (game permission → OS command, download → executable, config → shell string) without authentication or structured argument passing. v2 invariant: executables and scripts are fixed at install time and not changeable from in-game; processes are started with argument lists, never shell strings; downloaded code is verified against something that does not travel in the same archive; secrets are never logged.

**wrong-decision** — D-020, D-026, D-029, D-036, D-037, D-038, D-039, D-047, D-049, D-050, D-051, D-052, D-053, D-054, D-055, D-057, D-059, D-061, D-063, D-064, D-065, D-069, D-070, D-071, D-074, D-080, D-081, D-082, D-083, D-084, D-085, D-087, D-088, D-090, D-091, D-093, D-094, D-097, D-098, D-109, D-110, D-115, D-119, D-122, D-129 (45)
Root cause: decisions are taken from heuristics and from "unknown" collapsed into "no" or "yes" (failed query = mismatch, network error = unknown = update, text match = success), with caches and counters that are not tied to what they describe. v2 invariant: every remote fact has three explicit states (value, unchanged, failed-to-determine), a failed determination never authorises a change, and each decision is frozen with the exact versions it was made for.

**state-corruption** — D-005, D-007, D-013, D-019, D-028, D-034, D-041, D-042, D-044, D-048, D-058, D-060, D-072, D-078, D-079, D-089, D-111, D-124, D-126 (19)
Root cause: shared state (server tree, lock, marker, config, backend flag) is touched without ownership rules, while the server may be running, and by read-modify-write without atomicity. v2 invariant: files of a server are modified only while that specific server instance is proven stopped and the lock is held; the lock is taken before the server stops and released by its owner; every state file is written atomically and parsed with a real parser.

**self-update** — D-024, D-030, D-031, D-032, D-092, D-096 (6)
Root cause: plugin and app are updated by two programs in two steps with one version number, no transaction and no fallback. v2 invariant: self-update is opt-in, versioned per component, staged completely and verified before anything live is replaced, keeps the previous version until the new one has run, and a half-applied update is detected and retried.

**usability** — D-035, D-040, D-045, D-046, D-067, D-073, D-076, D-095, D-099, D-100, D-104, D-105, D-106, D-107, D-108, D-112, D-113, D-116, D-120, D-121, D-123, D-125, D-127, D-130 (24)
Root cause: diagnostics and contracts were added ad hoc (free-text reasons, one-line-per-file logs, untyped marker, documentation drifting from code). v2 invariant: one typed, versioned result document and one bounded, rotated log per run; user-facing messages come from a single table; documentation and examples are generated from or tested against the code's defaults.

**dead-code/duplication** — D-101, D-102, D-103 (3)
Root cause: features were added by copy-and-edit, and the same parser or probe lives in both programs. v2 invariant: each rule (path layout, VDF parse, marker shape, launcher) exists once, in the component that owns it, and unused arguments or branches are removed rather than carried.
